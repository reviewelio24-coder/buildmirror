# BuildMirror PRD

> AI가 만든 코드를 이해하고, 검증하고, 책임질 수 있게 만드는 서비스

**제품 정의:** 코드를 대신 설명하는 AI를 넘어, 코드가 기술적으로 타당하고 해당 저장소에 자연스럽게 맞으며 사용자가 그 판단 근거를 설명할 수 있는지 증명하는 AI 코드 오너십 플랫폼.

|----------------|-----------------------------------------------------------|
| 버전           | v0.2 — 다중 프로젝트·저장소 전환 반영                     |
| 작성일         | 2026년 8월 30일                                           |
| 상태           | 검토용 개정안                                             |

## 핵심 명제

좋은 AI 코드는 사람의 코드를 흉내 낸 코드가 아니다. 프로젝트의 기존 관습과 의사결정에 맞고, 소유자가 왜 그렇게 작성됐는지 설명하며 문제가 생겼을 때 수정할 수 있는 코드다.

# 1. Executive Summary

Cursor·Claude Code·Codex 같은 AI 코딩 도구는 초급자와 비개발자도 빠르게 서비스를 만들 수 있게 했다. 그러나 생성 속도가 이해 속도를 앞지르면서 새로운 문제가 생겼다. 코드는 작동하지만 만든 사람이 구조·권한·데이터 흐름·기술 선택을 설명하지 못하고, AI가 만든 변경이 기존 프로젝트의 관습과 어긋나도 이를 판별하기 어렵다.

BuildMirror는 이 간극을 해결한다. GitHub 저장소를 연결하면 프로젝트를 분석해 설명을 제공하고, 빌드·타입·테스트·보안·접근성 검사를 수행한다. 동시에 저장소의 기존 패턴과 커밋 이력에서 Repository Fingerprint를 만들고, 새 코드가 그 프로젝트다운 방식으로 작성됐는지 평가한다. 마지막으로 사용자가 주요 코드와 판단 근거를 직접 설명하도록 질문하고, 답변을 실제 코드 근거와 비교해 Developer Ownership을 측정한다.

> **핵심 차별점:** 설명 생성이 기본 기능이라면, BuildMirror의 제품 가치는 Technical Correctness · Repository Nativeness · Developer Ownership을 연결해 지속적으로 검증하는 데 있다.

# 2. 문제 정의

## 2.1 사용자가 겪는 문제

- AI가 생성한 코드가 실행되면 우선 받아들이지만 내부 구조와 위험을 판단하지 못한다.

- 코드 리뷰 AI는 일반적인 모범 사례를 말하지만 해당 프로젝트의 관습과 의도를 충분히 반영하지 못한다.

- 자동 생성 설명은 읽는 순간 이해한 것처럼 느껴지지만 실제로 설명하거나 수정할 수 있는지는 검증하지 않는다.

- 포트폴리오 면접에서 본인이 만든 기능의 데이터 흐름·기술 선택·보안 대책을 답변하지 못한다.

- 커밋이 쌓일수록 본인이 이해하지 못하는 코드 영역도 함께 누적된다.

## 2.2 기존 도구의 한계

| **도구 범주**     | **잘하는 것**              | **남는 문제**                                           |
|-------------------|----------------------------|---------------------------------------------------------|
| AI 코딩 도구      | 코드 생성·수정·설명        | 생성된 코드에 대한 소유자의 이해를 증명하지 않음        |
| 코드 리뷰 도구    | 버그·보안·품질 문제 탐지   | 일반 규칙 중심이며 프로젝트다운 판단과 학습 연결이 약함 |
| 코드베이스 문서화 | 구조도·위키·코드 투어 생성 | 수동적 소비에 머물고 이해도를 측정하지 않음             |
| 면접 연습         | 질문·답변 피드백           | 실제 커밋과 코드 품질 변화에 지속적으로 연결되지 않음   |

# 3. 제품 비전과 포지셔닝

비전: AI와 함께 개발하는 모든 사람이 자신이 배포하는 코드의 작동 방식과 판단 근거를 설명하고 책임질 수 있게 한다.

포지셔닝: BuildMirror는 AI 코드 탐지기나 코드 인간화 도구가 아니다. AI가 만든 코드를 프로젝트의 맥락과 개발자의 판단이 담긴 코드로 전환하는 AI Code Ownership Platform이다.

| **구분**       | **정의**                                                    |
|----------------|-------------------------------------------------------------|
| 하지 않는 주장 | AI가 쓴 코드인지 정확히 판별한다.                           |
| 하지 않는 주장 | 모든 코드를 인간 개발자가 작성한 것처럼 위장한다.           |
| 제공하는 가치  | 기술적 증거로 코드의 타당성을 검증한다.                     |
| 제공하는 가치  | 저장소의 기존 관습과 얼마나 자연스럽게 맞는지 평가한다.     |
| 제공하는 가치  | 사용자가 코드의 의도·위험·영향을 설명할 수 있는지 측정한다. |

## 4.1 MVP 핵심 페르소나

비전공 또는 초급 프런트엔드 개발자로, Cursor를 사용해 Next.js·Supabase 프로젝트를 완성했다. 서비스는 작동하지만 어떤 파일이 핵심인지, 데이터가 어떻게 이동하는지, RLS가 무엇을 보호하는지, AI가 만든 추상화가 필요한지 자신 있게 설명하지 못한다. 취업 면접이나 실제 배포 전에 프로젝트를 제대로 이해하고 싶다.

# 5. 제품 원칙

- Evidence before opinion — AI의 감상보다 실행 결과·코드 위치·기존 패턴을 먼저 제시한다.

- Explain before assess — 사용자가 판단할 수 있도록 충분한 설명을 기본 제공한다.

- Assess before auto-fix — 이해 없이 자동 수정부터 하지 않는다.

- Repository-native over universally human-like — 사람처럼 보이는 코드보다 이 저장소에 자연스러운 코드를 목표로 한다.

- Uncertainty is visible — 요구사항이나 실행 환경이 부족하면 신뢰도를 낮추고 판단 불가를 명시한다.

- Ownership over memorization — 정답 암기보다 의도·영향·대안을 설명하는 능력을 평가한다.

- Privacy by design — 분석에 필요한 최소 코드만 처리하고 비밀정보와 민감 데이터를 보호한다.

# 7. Repository Nativeness

## 7.1 Repository Fingerprint

저장소에서 반복되는 표현과 설계 패턴을 구조화한 프로젝트 코딩 지문이다. 반복된다는 이유만으로 좋은 패턴이라고 단정하지 않으며, 외부 레퍼런스와 프로젝트 헌법으로 보정한다.

| **영역** | **수집 신호**                      | **평가 예시**                |
|----------|------------------------------------|------------------------------|
| 명명     | 파일·컴포넌트·함수·변수 이름       | useX 훅과 동사형 함수 규칙   |
| 구조     | 폴더 배치·모듈 경계·import 방향    | UI에서 DB 직접 호출 여부     |
| 데이터   | Supabase 호출·서버/클라이언트 경계 | 공통 데이터 접근 함수 재사용 |
| 오류     | throw·result·toast·logging 패턴    | 오류를 삼키는 신규 catch     |
| 추상화   | 훅·서비스·유틸리티 분리 기준       | 단일 구현에 과도한 계층 추가 |
| 테스트   | 위치·네이밍·fixture·mock 관습      | 기존 테스트 방식과 일치      |
| 변경     | 커밋 크기·수정 경로·리팩터링 이력  | 작은 기능에 과도한 파일 변경 |

## 7.2 Project Constitution

분석 결과에서 프로젝트 규칙 후보를 생성하고 사용자가 승인·수정한다. 확정된 규칙은 이후 리뷰와 코드 생성의 상위 기준으로 사용한다.

- 서버 데이터는 가능한 한 Server Component에서 먼저 조회한다.

- Supabase 클라이언트 생성은 지정된 모듈을 사용한다.

- 단일 화면 전용 로직은 성급하게 공통화하지 않는다.

- 코드 내용을 번역하는 주석은 작성하지 않는다.

- 접근 권한은 프런트엔드 상태가 아니라 서버·DB 정책으로 보장한다.

## 7.3 기준의 우선순위

1.  명시적으로 승인된 Project Constitution

2.  프로젝트 요구사항·ADR·PR·Issue에서 확인된 의도

3.  저장소의 검증된 기존 패턴과 수용된 커밋

4.  동일 스택의 공식 문서와 사용자가 지정한 레퍼런스 저장소

5.  일반적인 언어·프레임워크 모범 사례

# 8. 핵심 사용자 경험

## 8.1 최초 분석 흐름

1.  GitHub 로그인 후 저장소 선택

2.  분석 범위·브랜치·민감 경로 확인

3.  의존성 설치·정적 분석·빌드 실행

4.  프로젝트 구조·데이터 흐름·핵심 파일 생성

5.  Repository Fingerprint 및 Constitution 후보 생성

6.  사용자가 프로젝트 목적과 핵심 기능 확인

7.  3축 점수·위험·학습 경로 제공

## 8.2 커밋 학습 루프

1.  GitHub push webhook 수신

2.  이전 분석과 diff 비교

3.  변경 영향과 새 개념 추출

4.  정확성·저장소다움 평가

5.  중요도에 따라 설명 카드 생성

6.  사용자에게 서술형·선택형·코드 추적 질문

7.  답변을 코드 근거와 비교 평가

8.  취약 개념을 다음 세션에 재출제

## 8.3 수정 제안 흐름

BuildMirror는 문제를 발견하자마자 코드를 덮어쓰지 않는다. 먼저 근거와 기존 유사 패턴을 제시하고 사용자의 판단을 확인한다. 수정안은 diff 형태로 제공하며, 승인 전에는 저장소에 쓰지 않는다.

## 8.4 다중 프로젝트 전환 흐름

사용자 계정 아래 여러 프로젝트를 등록한다. 프로젝트는 각각 연결 저장소, 분석 스냅샷, Repository Fingerprint, Project Constitution, 점수, 학습 기록을 독립적으로 가진다. 사용자가 A 프로젝트에서 B 프로젝트로 이동하면 B의 마지막 정상 분석을 즉시 표시하고 GitHub의 최신 커밋 SHA를 가볍게 확인한다.

1.  프로젝트 선택기에서 B 프로젝트 선택

2.  A의 마지막 메뉴·분석 버전·학습 초안 상태 저장

3.  B의 저장된 대시보드 즉시 표시

4.  B의 저장 분석 SHA와 GitHub 최신 SHA 비교

5.  변경이 없으면 최신 상태 표시

6.  변경이 있으면 기존 결과를 유지하며 증분 분석 선택 제공

7.  분석 시작 시 백그라운드 작업으로 전환하고 다른 프로젝트 이동 허용

8.  완료 후 알림과 이전 분석 대비 점수·finding 변화 제공

## 8.5 프로젝트 상태 모델

| **상태**         | **사용자 표시**                         | **시스템 처리**                       |
|------------------|-----------------------------------------|---------------------------------------|
| Up to date       | 분석 결과가 최신입니다.                 | 저장된 분석을 즉시 표시               |
| Changes detected | 새 커밋 N개가 발견됐습니다.             | 기존 결과 유지, 증분 분석 제안        |
| Analyzing        | 변경분을 분석하고 있습니다.             | 백그라운드 작업·단계별 진행률         |
| Stale            | 현재 GitHub 상태를 확인하지 못했습니다. | 기준 SHA·시간을 명시해 이전 결과 표시 |
| Failed           | 최신 분석에 실패했습니다.               | 실패 원인 제공, 이전 정상 분석 보존   |
| Disconnected     | GitHub 연결이 끊겼습니다.               | 읽기 전용 기록 유지, 재연결 유도      |
| Archived         | 보관된 프로젝트입니다.                  | 자동 감지 중지, 기존 결과 열람        |

## 8.6 저장소·브랜치 변경 정책

프로젝트 전환, 연결 저장소 변경, 분석 브랜치 변경을 구분한다. 다른 프로젝트를 보는 것은 기록에 영향을 주지 않는다. 저장소를 교체할 때는 기존 분석 보관을 기본값으로 하며, 코드 이력이 연속적이지 않으면 새 프로젝트 생성을 권고한다. 브랜치별 분석 계보는 분리하되 MVP에서는 기본 브랜치 하나만 활성 분석한다.

# 11. 분석 및 판정 파이프라인

1.  수집: GitHub 메타데이터, 선택 브랜치, 파일 트리, diff, package/lockfile, 설정 파일을 가져온다.

2.  보호: 비밀값·바이너리·생성 산출물·대형 파일을 제외하고 민감정보를 탐지한다.

3.  구문 분석: TypeScript Compiler API·Tree-sitter 등으로 심볼·import·호출 관계를 추출한다.

4.  실행 검증: 격리 워커에서 install·build·lint·typecheck·test를 실행한다.

5.  규칙 분석: ESLint·Semgrep·dependency audit·접근성 검사를 실행한다.

6.  저장소 모델링: 구조 그래프, Repository Fingerprint, Constitution 후보를 만든다.

7.  LLM 추론: 수집된 증거를 바탕으로 의도·영향·대안·학습 설명을 생성한다.

8.  교차 검증: 중요한 주장에 파일·심볼·실행 로그·규칙 ID를 연결한다.

9.  사용자 평가: 코드 근거 기반 질문을 출제하고 Ownership을 업데이트한다.

> **판정 규칙:** AI가 발견했지만 실행 또는 코드 근거로 확인되지 않은 내용은 “오류”가 아니라 “추가 검토 필요”로 표시한다.

## 11.1 분석 스냅샷과 캐시 정책

분석 결과는 프로젝트당 하나가 아니라 브랜치·커밋별 불변 스냅샷으로 저장한다. 화면을 열 때는 최신 커밋 확인만 수행하고 기존 스냅샷을 즉시 보여준다. 전체 재분석은 기술 스택·구조·분석 엔진·Constitution이 크게 바뀌거나 변경량이 임계치를 넘을 때만 실행한다.

| **캐시 키**                 | **역할**                         |
|-----------------------------|----------------------------------|
| user_id · project_id        | 사용자와 프로젝트 경계           |
| repository_id · branch_name | 저장소와 분석 계보               |
| commit_sha                  | 코드의 정확한 버전               |
| analysis_engine_version     | 분석 규칙·도구 버전              |
| constitution_version        | Repository Native 평가 기준 버전 |

| **점수**              | **하위 항목**                                                  | **초기 가중치** |

각 점수에는 Confidence를 별도로 표시한다. 요구사항·테스트·실행 환경·기준 저장소가 부족할수록 신뢰도가 낮아진다. 종합 점수는 사용자에게 방향을 제공하지만 개별 근거와 차단 이슈보다 우선하지 않는다.

## 13.1 환각 억제 원칙

- 존재하지 않는 파일·함수·설정을 인용하지 않는다.

- 코드 근거가 없는 의도는 “추정”으로 표시한다.

- 요구사항이 없으면 기능 오류를 단정하지 않는다.

- 공식 문서 대조 시 설치된 실제 버전을 기준으로 한다.

- 동일 문제에 대해 비판 관점과 합리적 예외 가능성을 함께 검토한다.

- 근거가 충돌하면 자동 수정하지 않고 사용자 확인을 요청한다.

## 14.1 보안 경계

- GitHub App은 읽기 전용 최소 권한을 기본으로 한다.

- 자동 수정은 별도 권한과 매번의 사용자 승인을 요구한다.

- 저장소 실행은 네트워크·CPU·메모리·시간이 제한된 일회성 컨테이너에서 수행한다.

- 환경변수와 비밀키는 모델 입력에 포함하지 않고 마스킹한다.

- private repository 원문 보존 기간과 삭제 정책을 명확히 제공한다.

- 사용자별 Supabase RLS로 프로젝트·리포트·답변을 격리한다.

# 23. 출시 수용 기준

- GitHub App으로 저장소를 연결하고 선택 브랜치의 commit SHA를 고정해 분석할 수 있다.

- 한 계정에서 A와 B 프로젝트를 생성하고 검색·전환할 수 있다.

- 프로젝트를 전환하면 저장된 정상 분석이 즉시 표시되고 각 프로젝트의 규칙·점수·학습 기록이 섞이지 않는다.

- 프로젝트를 열 때 저장 SHA와 GitHub 최신 SHA를 비교하고 변경 여부를 표시한다.

- 변경분 분석 중 다른 프로젝트로 이동해도 작업이 계속되고 완료·실패 알림을 받는다.

- 신규 분석이 실패해도 이전 정상 스냅샷을 열람할 수 있다.

- 분석 스냅샷이 project·repository·branch·commit·engine·constitution 버전으로 식별된다.

- 프로젝트를 보관하면 자동 변경 감지가 중지되고 기존 결과는 유지된다.

- Next.js·TypeScript 프로젝트에서 구조·핵심 진입점·Supabase 호출을 추출한다.

- build·typecheck·lint 결과를 성공·실패·미지원으로 구분해 저장한다.

- 중요 finding에는 최소 하나의 재현 가능한 근거가 연결된다.

- Repository Fingerprint와 Constitution 후보가 생성되고 사용자가 승인·수정할 수 있다.

- 새 commit diff에서 기존 관습과 다른 변경을 근거와 함께 보여준다.

- 설명 카드 후 사용자가 서술 답변을 제출하고 0~4 루브릭 평가를 받는다.

- 3축 점수와 Confidence가 commit 단위로 기록된다.

- private repo 연결 해제와 저장 데이터 삭제가 가능하다.

- AI가 생성한 수정은 사용자의 명시적 승인 전 저장소에 반영되지 않는다.
